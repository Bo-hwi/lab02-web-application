# HW3 AI-Assisted Work: Failure and Risk Audit

This audit reviews incomplete intermediate revisions made during AI-assisted work on `hw3/flash-sale`. The snapshots and fixes below are verifiable in Git. Git records the student's account as author and cannot establish which individual lines were generated by an assistant. Accordingly, these are observed **AI-assisted review failures or risks**, not claims of proven AI authorship. The intermediate gaps were corrected before T12; they are not presented as defects in the current branch.

To inspect an old snapshot without changing the working tree, use `git show <commit>:<path>`. To run an old version in a browser, create a separate temporary checkout with `git worktree add --detach <folder> <commit>`, serve that folder over HTTP, then remove the worktree when done. Do not switch the submission checkout while it has uncommitted changes.

## 1. Hold expiry did not redraw the page immediately

- **Symptom:** In the T08 browser revision, a hold could expire in the controller while its product card still showed the old hold until a later user action or the sale-end redraw. That made available stock and the action buttons temporarily stale.
- **Affected code:** `js/sale/main.js` at `23e98d8`. It rendered on actions and at sale close, but had no inventory subscription to redraw on scheduled expiry.
- **Reproduce:** Run `git show 23e98d8:js/sale/main.js` and inspect the event/timer paths; there is no `subscribeInventory` call. In a temporary T08 checkout, reserve Midnight Earbuds and wait past its 30-second hold without interacting. Compare the card with a fresh action after expiry.
- **Fix:** `72539d7` connected `controller.subscribeInventory(onInventoryChange)`, updated the card and announced the expired hold. `js/sale/controller.js` exposes inventory-change subscriptions and removes them on disposal.
- **Retest:** The recorded T09 browser check observed stock return from 1 to 2 and Reserve reappear automatically after 30 seconds. Controller subscription tests were included in the 38/38 T09 Node result; see `docs/verification/HW3_VERIFICATION.md`.
- **Attribution:** The incomplete revision arose in an AI-assisted implementation sequence. Git alone does not identify whether the missing subscription was an AI-generated omission or a human integration choice.

## 2. The first browser timer lacked coarse spoken milestones

- **Symptom:** The T09 interface had a visible timer, but it had no separate sale-announcement region for ten-second milestones or each of the final five seconds. A user relying on status announcements had less time context than the contract required.
- **Affected code:** `js/sale/main.js` at `72539d7`. `onTick` changed the clock text and handled zero but had no milestone announcement branch.
- **Reproduce:** Inspect `git show 72539d7:js/sale/main.js` and search for `saleAnnouncement` or a `totalSeconds % 10` check. In a temporary checkout, inspect the live-region text while the timer runs; routine time changes were not announced there.
- **Fix:** `d4c86a1` added the separate polite sale-announcement status and code for ten-second and final-five-second notices, while leaving the every-second timer at `aria-live="off"`.
- **Retest:** The T10 browser accessibility-tree review observed ten-second milestone text and the final sale-ended message. The final-five-second branch was inspected in source but not individually observed in that browser run; see `docs/verification/HW3_VERIFICATION.md`.
- **Attribution:** This was an incomplete AI-assisted draft relative to the written contract. The commit author field does not prove who omitted the milestone logic.

## 3. The pre-T11 page had no Reset control

- **Symptom:** A visitor could not start a fresh sale on the same page after spending stock or waiting for sale closure, despite the T02 contract requiring Reset to start a new run and dispose old resources.
- **Affected code:** `index.html` and `js/sale/main.js` at `d4c86a1`. There was no `reset-sale` button or session factory; the controller and deadline were created once.
- **Reproduce:** Inspect `git show d4c86a1:index.html` and `git show d4c86a1:js/sale/main.js`; neither contains a Reset action. In a temporary checkout, complete checkout or wait for the sale to end and look for a way to restore initial stock without reloading.
- **Fix:** `0fdf950` added a native Reset button, `startSession()` and `disposeSession()`. A new session restores fixture stock, restarts the five-minute deadline and disposes the previous timer, subscription and controller.
- **Retest:** The T11 browser check reserved Midnight Earbuds, pressed Reset, saw stock return from 1 to 2 and the timer return to `05:00`, then repeated Reset twice without a JavaScript error. Two lifecycle tests covered disposal across 20 cycles and ignored late callbacks; see `docs/verification/HW3_VERIFICATION.md`.
- **Attribution:** This was a requirement gap in an AI-assisted intermediate revision. The change was planned for T11, so this finding does not imply that the T10 milestone was falsely declared complete or prove AI authorship.

## Additional lifecycle risk: back-forward cache restoration

At `d4c86a1`, `js/sale/main.js` disposed its timer and controller on `pagehide` but had no `pageshow` recovery. A page restored from the browser back-forward cache could therefore retain a disposed session. `0fdf950` added a `pageshow` handler that starts a new session when `event.persisted` is true. This conclusion follows from the source control flow; a real browser back-forward-cache restoration was not separately observed in the T11 verification and is not counted among the three retested findings above.
